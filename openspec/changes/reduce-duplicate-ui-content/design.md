## Context

Клиентское Next.js 13 (App Router) демо «Корподарки» на mock-данных. Пользовательские тексты и контролы рассредоточены по страницам (`app/(app)/page.tsx`, `app/(app)/faq/page.tsx`, `app/(auth)/login/page.tsx`), общим компонентам (`components/layout/*`, `components/features/*`) и метаданным (`app/layout.tsx`). Подписи причин возврата формирует `lib/data-store.ts:reasonLabel`, но рядом существуют хардкод-строки в `components/features/AdminTable.tsx`. Часть `components/ui/*` не импортируется ни из достижимого кода.

Спецификации проекта в `openspec/specs/` пусты; доменные delta (`donations`, `support-chat`) живут в незаархивированных изменениях `fix-known-gaps` и `fix-qa-reported-defects`. Требование `fix-qa-reported-defects` обязывает текст шага почты направлять к кнопке «Оставить пожелание», поэтому при дедупликации нельзя удалять эту подсказку — только дублирующую фразу о скрытии сумм. См. `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Оставить одно каноническое сообщение о добровольности и скрытых суммах (футер) и не более одного контекстного упоминания на страницу.
- Свести формулировки причин возврата к единственному источнику `reasonLabel`.
- Оставить один первичный контроль для пожелания без взноса на главной.
- Убрать неинтерактивный пункт меню и дублирующую разметку навигации.
- Удалить недостижимые UI-примитивы без изменения поведения приложения.

**Non-Goals:**

- Не меняются правила валидации суммы, модель ролей, авторизация, темы и источник аватаров.
- Не вводится персистентность (данные остаются in-memory).
- Не переписывается сценарий участия и не меняется набор его шагов.

## Decisions

1. **Каноническое сообщение — футер; на главной остаётся один контекстный блок.**
   `components/layout/Footer.tsx` сохраняет полное утверждение. На главной удаляются hero-бейдж «Участие добровольное» (дублирует абзац hero) и две privacy-карточки («Добровольное участие», «Суммы скрыты»), повторяющие hero. Блок из трёх карточек заменяется одной компактной карточкой, сохраняющей недублирующий смысл «Команда — это важно».
   - Почему: убирает визуальное дублирование, не теряя полезный третий мессендж.
   - Альтернатива: удалить все три карточки и оставить только футер — отклонено, теряется сообщение о командной ценности.

2. **FAQ: ответы становятся единственным источником.**
   Из `app/(app)/faq/page.tsx` удаляются три quick-info карточки, повторяющие ответы Q1/Q2 и текст главной; аккордеон с ответами остаётся.
   - Почему: карточки не добавляли информации сверх ответов.
   - Альтернатива: оставить карточки, а ответы сократить — отклонено, ответы содержат обязательные пояснения.

3. **В диалоге участия — одно пояснение о скрытии суммы, подсказка про доску сохраняется.**
   В `components/features/DonateDialog.tsx` на шаге `email` сохраняется направление к кнопке «Оставить пожелание», но убирается фраза о видимости суммы; из описания шага `amount` убирается повтор про скрытие итога; единственное пояснение о скрытии суммы остаётся на шаге `confirm` (там пользователь подтверждает действие). Для администратора пояснение о скрытии не показывается.
   - Почему: не конфликтует с требованием `fix-qa-reported-defects` о подсказке к доске и оставляет ровно одно упоминание скрытия.
   - Альтернатива: оставить пояснение на шаге `email`, убрав на `confirm` — отклонено, подтверждение — точка принятия решения, пояснение уместнее там.

4. **Один первичный контроль пожелания на главной.**
   `app/(app)/page.tsx` hero-кнопка «Оставить пожелание» остаётся единственным первичным контролом: она скроллит к доске и открывает форму. `components/features/WishBoard.tsx` при заданном пропе `formOpen` перестаёт рендерить собственный тоггл; внутренняя кнопка-тоггл сохраняется только в uncontrolled-режиме (когда `formOpen` не передан), чтобы компонент оставался самодостаточным.
   - Почему: убирает два одновременных контрола одного действия, не ломая переиспользование компонента.
   - Альтернатива: удалить hero-кнопку и оставить тоггл доски — отклонено, hero остаётся основной точкой входа.

5. **Навигация шапки рендерится один раз.**
   В `components/layout/Header.tsx` список `navItems` и admin-ссылка рендерятся единой функцией/подкомпонентом с параметром класса для desktop и mobile, вместо двух копий JSX. Активное состояние по-прежнему вычисляется по `pathname`.
   - Почему: устраняет расхождение двух копий при правках.
   - Альтернатива: оставить две копии — отклонено, это источник будущих расхождений.

6. **Отдел в меню пользователя — неинтерактивная строка.**
   В `Header.tsx` отдел отображается как информационный текст внутри меню (не `DropdownMenuItem`), чтобы не выглядеть командой.
   - Почему: элемент не выполняет действие, а стиль пункта меню вводит в заблуждение.
   - Альтернатива: удалить строку совсем — отклонено, отдел полезен как контекст.

7. **`reasonLabel` — единственный источник подписей причин.**
   В `AdminTable.tsx` подписи радиоопций формируются через `reasonLabel`; остаются только самостоятельные поясняющие подписи (не повторяющие название причины). Дублирующие хардкод-названия причин удаляются.
   - Почему: одна причина — одна формулировка в выборе и журнале.
   - Альтернатива: продублировать карту причин — отклонено, снова разъедется.

8. **Удаление недостижимых UI-примитивов.**
   Удаляются 30 файлов `components/ui/*` без ссылок, а также «остров» уведомлений (`hooks/use-toast.ts`, `toast.tsx`, `toaster.tsx`, `sonner.tsx`) и `toggle.tsx`/`toggle-group.tsx`, которые импортируются только друг другом. Перед удалением перепроверяется отсутствие импортов; после — `npm run typecheck` и `npm run lint`.
   - Почему: файлы недостижимы из приложения; удаление безопасно и сокращает базу.
   - Альтернатива: оставить как есть — отклонено, это мёртвый код.

9. **Метаданные и логин не дублируют гарантию.**
   `app/layout.tsx` (SEO-описание) и подзаголовок `app/(auth)/login/page.tsx` сводятся к короткой брендовой формулировке, не повторяющей полное предложение футера. Метаданные не рендерятся в UI и остаются отдельным источником для SEO.
   - Почему: убирает второй полный вариант того же утверждения.
   - Альтернатива: убрать описание из метаданных — отклонено, вредит SEO.

## Risks / Trade-offs

- [Удалённый примитив может понадобиться в новой фиче] → Перед удалением сверить импорты grep'ом; удаление обратимо через git; воссоздание стандартного shadcn-примитива дешёвое.
- [Конфликт с `fix-qa-reported-defects` по тексту шага почты] → Сохранить указание на «Оставить пожелание», удалить только фразу о скрытии суммы; при архивации согласовать формулировки.
- [Конфликт с доменными delta `donations`/`support-chat` из незаархивированных изменений] → `ui-consistency` не меняет правила поведения, только размещение текстов; при синхронизации сначала архивировать доменные изменения.
- [Один контроль пожелания ухудшит доступность формы на мобильных] → WishBoard сохраняет uncontrolled-режим с внутренним тогглом; на главной форма открывается hero-кнопкой и доступна с клавиатуры.
- [Дедупликация навигации может сломать активные состояния] → Проверить оба варианта (desktop/mobile) и подсветку текущего раздела.
- [Удаление текстов может убрать полезный контекст] → Оставлять по одному упоминанию на страницу и проверять, что информация не потеряна полностью.

## Migration Plan

Порядок применения: сначала проверки импортов и удаление мёртвого кода, затем дедупликация текстов и контролов, затем `npm run typecheck`/`npm run lint` и прогон страниц `/`, `/faq`, `/calendar`, `/admin`, `/login`. Откат — стандартный revert коммита; миграции данных и совместимости не требуются.
