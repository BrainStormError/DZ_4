## Context

A client-side Next.js 13 (App Router) demo "Korporpodarki" on mock data. User texts and controls are scattered across pages (`app/(app)/page.tsx`, `app/(app)/faq/page.tsx`, `app/(auth)/login/page.tsx`), shared components (`components/layout/*`, `components/features/*`) and metadata (`app/layout.tsx`). Refund reason labels are generated by `lib/data-store.ts:reasonLabel`, but hardcoded strings exist alongside in `components/features/AdminTable.tsx`. Some of `components/ui/*` is not imported from reachable code.

The project specifications in `openspec/specs/` are empty; the domain deltas (`donations`, `support-chat`) live in the unarchived changes `fix-known-gaps` and `fix-qa-reported-defects`. The `fix-qa-reported-defects` requirement obliges the email step text to point to the "Leave a wish" button, so during deduplication this hint must not be removed — only the duplicate phrase about hiding amounts. See `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Keep a single canonical message about voluntariness and hidden amounts (the footer) and no more than one contextual mention per page.
- Reduce the refund reason wordings to a single source `reasonLabel`.
- Keep one primary control for a wish without a contribution on the home page.
- Remove the non-interactive menu item and the duplicate navigation markup.
- Delete unreachable UI primitives without changing the application's behavior.

**Non-Goals:**

- The amount validation rules, the role model, authorization, themes and the avatar source are not changed.
- No persistence is introduced (data remains in-memory).
- The participation scenario is not rewritten and the set of its steps is not changed.

## Decisions

1. **The canonical message is the footer; one contextual block remains on the home page.**
   `components/layout/Footer.tsx` keeps the full statement. On the home page, the hero badge "Participation is voluntary" (duplicates the hero paragraph) and two privacy cards ("Voluntary participation", "Amounts are hidden") repeating the hero are removed. The block of three cards is replaced by one compact card that preserves the non-duplicate meaning "The team matters".
   - Why: removes visual duplication without losing the useful third message.
   - Alternative: delete all three cards and leave only the footer — rejected, the message about team value is lost.

2. **FAQ: the answers become the only source.**
   Three quick-info cards repeating answers Q1/Q2 and the home page text are removed from `app/(app)/faq/page.tsx`; the accordion with the answers remains.
   - Why: the cards added no information beyond the answers.
   - Alternative: keep the cards and shorten the answers — rejected, the answers contain mandatory explanations.

3. **In the participation dialog — one explanation about hiding the amount, the board hint is preserved.**
   In `components/features/DonateDialog.tsx`, at the `email` step the pointer to the "Leave a wish" button is kept, but the phrase about amount visibility is removed; from the `amount` step description the repetition about hiding the total is removed; the only explanation about hiding the amount remains at the `confirm` step (where the user confirms the action). For an administrator the explanation about hiding is not shown.
   - Why: it does not conflict with the `fix-qa-reported-defects` requirement about the board hint and leaves exactly one mention of hiding.
   - Alternative: keep the explanation at the `email` step and remove it at `confirm` — rejected, confirmation is the decision point, so the explanation is more appropriate there.

4. **One primary wish control on the home page.**
   In `app/(app)/page.tsx` the hero button "Leave a wish" remains the only primary control: it scrolls to the board and opens the form. `components/features/WishBoard.tsx`, when the `formOpen` prop is set, stops rendering its own toggle; the internal toggle button is kept only in uncontrolled mode (when `formOpen` is not passed) so that the component remains self-contained.
   - Why: removes two simultaneous controls for one action without breaking component reuse.
   - Alternative: delete the hero button and keep the board toggle — rejected, the hero remains the main entry point.

5. **The header navigation is rendered once.**
   In `components/layout/Header.tsx` the `navItems` list and the admin link are rendered by a single function/subcomponent with a class parameter for desktop and mobile, instead of two copies of JSX. The active state is still computed from `pathname`.
   - Why: eliminates divergence of the two copies during edits.
   - Alternative: keep two copies — rejected, it is a source of future divergence.

6. **The department in the user menu is a non-interactive line.**
   In `Header.tsx` the department is displayed as informational text inside the menu (not a `DropdownMenuItem`) so that it does not look like a command.
   - Why: the item performs no action, and the menu item styling is misleading.
   - Alternative: remove the line entirely — rejected, the department is useful as context.

7. **`reasonLabel` is the only source of reason labels.**
   In `AdminTable.tsx` the radio option labels are generated via `reasonLabel`; only self-contained explanatory labels remain (that do not repeat the reason name). Duplicate hardcoded reason names are removed.
   - Why: one reason — one wording in the selection and the log.
   - Alternative: duplicate the reason map — rejected, it will diverge again.

8. **Removal of unreachable UI primitives.**
   30 unreferenced files `components/ui/*` are deleted, along with the notification "island" (`hooks/use-toast.ts`, `toast.tsx`, `toaster.tsx`, `sonner.tsx`) and `toggle.tsx`/`toggle-group.tsx`, which are imported only by each other. Before deletion, the absence of imports is rechecked; afterwards — `npm run typecheck` and `npm run lint`.
   - Why: the files are unreachable from the application; deletion is safe and reduces the codebase.
   - Alternative: leave as is — rejected, it is dead code.

9. **Metadata and login do not duplicate the guarantee.**
   `app/layout.tsx` (SEO description) and the subtitle of `app/(auth)/login/page.tsx` are reduced to a short brand wording that does not repeat the full footer sentence. Metadata is not rendered in the UI and remains a separate source for SEO.
   - Why: removes the second full variant of the same statement.
   - Alternative: remove the description from metadata — rejected, it harms SEO.

## Risks / Trade-offs

- [A deleted primitive may be needed in a new feature] → Before deletion, verify imports with grep; deletion is reversible via git; recreating a standard shadcn primitive is cheap.
- [Conflict with `fix-qa-reported-defects` over the email step text] → Keep the pointer to "Leave a wish", remove only the phrase about hiding the amount; during archiving, reconcile the wordings.
- [Conflict with the domain deltas `donations`/`support-chat` from unarchived changes] → `ui-consistency` does not change behavior rules, only text placement; during synchronization, archive the domain changes first.
- [A single wish control will worsen form accessibility on mobile] → WishBoard keeps uncontrolled mode with an internal toggle; on the home page the form is opened by the hero button and is keyboard accessible.
- [Navigation deduplication may break active states] → Check both variants (desktop/mobile) and the highlighting of the current section.
- [Removing texts may remove useful context] → Leave one mention per page and check that the information is not lost entirely.

## Migration Plan

Application order: first import checks and dead code removal, then deduplication of texts and controls, then `npm run typecheck`/`npm run lint` and a run of the pages `/`, `/faq`, `/calendar`, `/admin`, `/login`. Rollback is a standard commit revert; no data or compatibility migrations are required.
