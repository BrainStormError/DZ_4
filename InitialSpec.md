# Задача: сгенерировать 3 различные UI-концепции приложения «Корпоративные подарки»

## Стек (обязательно)
- Next.js 14+ (App Router)
- TypeScript
- Tailwind CSS
- shadcn/ui (все компоненты через CLI, не копипаст)
- lucide-react для иконок
- Без реального бэкенда: данные — моки в `/lib/mock-data.ts`, «авторизация» — мок через localStorage/context

## Контекст продукта
Корпоративное веб-приложение для добровольного сбора средств на подарки сотрудникам ко дню рождения.

**Ключевые правила:**
- Участие **добровольное** — это должно быть явно и заметно на главной.
- Обычные сотрудники **никогда** не видят суммы сборов (ни свои, ни чужие).
- Админ видит все суммы, но может менять их **только** в двух случаях: возврат из-за отказа поздравляемого от подарка, либо экстренный возврат по прямому запросу (с указанием причины).
- Вход — по корпоративной почте (мок-форма, без реальной аутентификации).
- На доске пожеланий автор отображается под ником = корпоративная почта.
- 2 роли: `employee`, `admin`.

**Обязательные страницы/разделы:**
1. **Главная** — объяснение цели сбора, акцент на добровольности, блок «Именинники сегодня», доска пожеланий, кнопка «Поздравить / отправить средства».
2. **Календарь ДР** — помесячный/годовой вид с ДР сотрудников, переключение по месяцам в рамках года (вперёд/назад в пределах текущего).
3. **FAQ** — вопросы-ответы + форма «Написать админу» (у каждого сотрудника — только своя ветка переписки).
4. **Модалка/страница сбора средств** — ввод корпоративной почты → подтверждение → мок-оплата.
5. **Админ-панель** — таблица сумм по всем сотрудникам, кнопка «Изменить» доступна **только** при выборе причины (возврат/отказ), журнал причин.

## Что мне нужно от тебя

Сгенерируй **три полноценные UI-концепции** одного и того же приложения, отличающиеся **визуальным стилем и настроением**, но с одинаковой структурой и функциональностью. Должна быть возможность переключаться на каждую концепцию внутри приложения.

Перед кодом — короткое резюме каждой концепции: название, палитра (hex), шрифты (Google Fonts), ключевые визуальные приёмы.

### Концепция A — «Тёплый праздник»
- Мягкие пастельные тона (кремовый, тёплый персиковый, приглушённое золото), округлые формы, лёгкие иллюстрации/эмодзи (🎂🎈), крупные скругления (`rounded-3xl`), плавные тени.
- Атмосфера: уют, доброта, семейное тепло.
- Шрифт: `Nunito` или `Comfortaa` для заголовков.

### Концепция B — «Корпоративный фестиваль»
- Яркая, энергичная палитра (фуксия, коралловый, тёплый жёлтый, акцентный фиолетовый), градиенты, стикеры-конфетти, динамичные карточки с лёгким наклоном, микровзаимодействия.
- Атмосфера: драйв, движ, командный дух.
- Шрифт: `Manrope` + акцидентный `Bricolage Grotesque` для заголовков.

### Концепция C — «Премиальный минимализм с праздником»
- Светлый фон (off-white), строгая типографика, много воздуха, единственный акцентный цвет (глубокий изумруд или бордо), точечные праздничные элементы (тонкие блёстки, аккуратные иконки конфетти).
- Атмосфера: элегантно, дорого, но с намёком на праздник.
- Шрифт: `Inter` + `Fraunces` для заголовков.

**Функциональные моки:**
- `mockUsers`: 8–12 сотрудников с полями `id, fullName, email, birthDate, department, avatarUrl`.
- `mockWishes`: доска пожеланий с полем `authorEmail` (ник = email).
- `mockDonations`: суммы по сотрудникам (видны только в админке).
- `mockChats`: переписка `email → [messages]` с админом.
- `mockDonationHistory`: журнал изменений сумм с причиной (`refund_declined | emergency_refund`) и комментарием.

**Логика, которую надо замокать (не только UI):**
- При открытии `DonateDialog` — сначала валидация корпоративной почты (regex `@company.com`), и только потом отображается поле суммы и кнопка «Отправить».
- Если роль `employee` — компонент суммы донатов скрыт полностью (не `disabled`, а `hidden`/не рендерится).
- В админке кнопка «Изменить сумму» открывает модалку, где **обязателен** выбор причины из двух вариантов + текст комментария. Без этого — сохранение заблокировано.
- Чат в FAQ: сотрудник видит только свою ветку (фильтр по текущей мок-сессии).

**Доступность и адаптив:**
- Mobile-first, breakpoints `sm/md/lg/xl`.
- Тёмная тема не требуется, но дизайн-токены должны быть через CSS-переменные (`--background`, `--primary` и т.д.) в `globals.css`, чтобы легко менять тему.

- Не подключать БД, NextAuth, Stripe, реальную почту.
- Не использовать другие UI-библиотеки кроме shadcn/ui.
- Не плодить кастомные компоненты там, где хватает shadcn.

## Основные данные по проекту (анализ текущей реализации)

### Назначение и режим работы

Демонстрационное веб-приложение для добровольного сбора средств на подарки сотрудникам ко дню рождения. Работает полностью на клиенте на mock-данных: без базы данных и бэкенда, состояние хранится в памяти и сбрасывается при перезагрузке страницы. Вход по корпоративной почте и отправка средств имитируются (мок) — реальные интеграции подключаются позже.

### Технологический стек

- Next.js 13.5 (App Router), React 18, TypeScript 5
- Tailwind CSS 3 и shadcn/ui (Radix UI), иконки lucide-react
- date-fns (даты, русская локаль), react-hook-form и zod (формы и валидация)
- Кастомные React-контексты для авторизации, данных и темы; выбор темы сохраняется в localStorage
- Деплой: Netlify (`netlify.toml`, `@netlify/plugin-nextjs`)

### Архитектура и маршруты

Корневой `app/layout.tsx` оборачивает приложение в `ThemeProvider` -> `AuthProvider` -> `DataProvider`. Защищённые страницы лежат в группе `app/(app)/` и закрыты `AuthGate`, который перенаправляет неавторизованных на `/login`.

| Маршрут | Экран |
| --- | --- |
| `/login` | вход по корпоративной почте |
| `/` | главная: именинники сегодня и скоро, доска пожеланий, отправка средств |
| `/calendar` | календарь дней рождения по месяцам |
| `/faq` | частые вопросы и переписка с администратором |
| `/admin` | панель администратора (только роль `admin`) |

Основные модули: `lib/auth-context.tsx` (вход, сессия в localStorage), `lib/data-context.tsx` и `lib/data-store.ts` (пожелания, сборы, журнал, чаты), `lib/theme-context.tsx` и `lib/theme.ts` (темы), `lib/mock-data.ts` (данные), `lib/types.ts` (типы). Бизнес-компоненты — в `components/features/`, каркас — в `components/layout/`, UI-набор — в `components/ui/`.

### Модель данных

- `User`: id, ФИО, корпоративная почта, дата рождения, отдел, аватар, роль (`employee` | `admin`)
- `Wish`: id, почта автора, id получателя, текст, дата создания
- `Donation`: id пользователя и сумма сбора
- `DonationHistoryEntry`: сотрудник, админ, прежняя и новая сумма, причина (`refund_declined` | `emergency_refund`), комментарий, дата
- `ChatThread` и `ChatMessage`: ветка по почте сотрудника; сообщение с автором, текстом, признаком администратора и датой

### Роли и доступ

| Возможность | Сотрудник | Администратор |
| --- | --- | --- |
| Вход по почте `@company.com` из справочника | да | да |
| Просмотр именинников и календаря | да | да |
| Доска пожеланий (автор под ником до `@`) | да | да |
| Участие в сборе после подтверждения почты | да | да |
| Просмотр сумм сбора | нет | да, по всем сотрудникам |
| Изменение суммы | нет | только возвраты с обязательной причиной и комментарием |
| Журнал изменений сумм | нет | да |
| Переписка с администратором | только своя ветка | да |
| Пункт «Админ» в шапке | скрыт | показан |

### Ограничения текущей реализации

- Суммы скрыты от сотрудников только на уровне интерфейса; данные доступны в памяти браузера, реальной защиты нет.
- Данные не персистентны и сбрасываются при перезагрузке.
- Год в календаре зафиксирован (2026), переход между годами отсутствует.
- В сценарии участия сотрудника сумма не вводится, а пожелание не создаётся, хотя интерфейс обещает передать поздравление.
- Администратор не видит ветки обращений сотрудников: компонент переписки показывает только ветку текущего пользователя.

### Области спецификации (capabilities)

- `auth` — вход по корпоративной почте и единая проверка корпоративного адреса
- `birthdays` — именинники на главной и календарь дней рождения
- `wishes` — доска пожеланий и создание поздравлений
- `donations` — подтверждение почты, сокрытие сумм, учёт участия
- `support-chat` — частые вопросы и приватная переписка с администратором
