# Корподарки

Приложение для добровольного сбора средств на подарки сотрудникам ко дню рождения.

Сотрудники могут оставлять пожелания, присоединяться к сбору, смотреть календарь дней рождений и переписываться с администратором. Администратор видит суммы сборов, управляет возвратами и ведёт журнал изменений.

> Это учебный демо-проект. Данные (сотрудники, пожелания, суммы сборов, журнал изменений и сообщения) хранятся в PostgreSQL и доступны всем пользователям: изменение сохраняется после перезагрузки страницы и перезапуска приложения. Вход выполняется через Google OAuth 2.0, а сессия хранится в подписанной `HttpOnly`-cookie.

## Конфигурация

Приложение читает строку подключения к базе из переменной окружения `DATABASE_URL`.
Скопируйте пример и заполните значения:

```bash
cp .env.example .env
```

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_DB` | имя базы данных (для сервиса `db`) |
| `POSTGRES_USER` | пользователь базы данных |
| `POSTGRES_PASSWORD` | пароль пользователя базы данных |
| `DATABASE_URL` | строка подключения приложения, например `postgresql://corp_gift:change-me@db:5432/corp_gift` |
| `GOOGLE_CLIENT_ID` | идентификатор клиента Google OAuth 2.0 |
| `GOOGLE_CLIENT_SECRET` | секрет клиента Google OAuth 2.0 |
| `NEXTAUTH_SECRET` | секрет подписи сессионной cookie (например, `openssl rand -base64 32`) |
| `REGISTRATION_TICKET_SECRET` | отдельный секрет подписи ticket регистрации; должен отличаться от `NEXTAUTH_SECRET` |
| `NEXTAUTH_URL` | публичный HTTPS-адрес, по которому пользователи реально открывают приложение |
| `DEMO_LOGIN` | `1` включает демо-вход по тестовым адресам на `/login`; любое другое значение (в том числе отсутствие) оставляет вход только через Google |

Файл `.env` не коммитится. Если `DATABASE_URL` не задан, приложение не подменяет данные встроенными значениями, а сообщает об ошибке подключения. Если `NEXTAUTH_SECRET` или `REGISTRATION_TICKET_SECRET` не заданы или оставлены примером из `.env.example`, приложение сообщает об ошибке конфигурации вместо запуска входа.

### Граница допуска и эксплуатационные требования ко входу

Вход выполняется через Google OAuth 2.0. **Граница допуска открыта по замыслу**: любой аккаунт, подтверждённый Google, может войти и зарегистрироваться, и никакое ограничение по домену адреса не применяется. Эта граница защищает только от подделки личности (адрес подтверждается провайдером), но не ограничивает круг допущенных людей. Развёртывание содержит только демонстрационные данные.

Для продакшен-эксплуатации эта граница недостаточна. Перед допуском реальных людей потребуется дополнительно одно из: ограничение по адресу или тенанту, шаг с приглашением, либо аутентифицирующий прокси перед приложением.

У развёрнутого стека должны быть выполнены условия:

- **Исходящий доступ по HTTPS к эндпоинтам Google** (`accounts.google.com`, `oauth2.googleapis.com` и связанным с ними). Без egress вход невозможен.
- **Адрес обратного вызова, который реально достижим.** Значение `NEXTAUTH_URL` должно совпадать с публичным адресом приложения и с redirect URI, зарегистрированным в Google Cloud: `https://<публичный-хост>/api/auth/callback/google`. Если адрес не совпадает, вход завершается сообщением об ошибке, а не «зависанием».

TLS завершается на хосте перед приложением, поэтому внешний адрес всегда `https://…`. Сессионная cookie и cookie ticket регистрации в продакшене всегда помечаются флагом `Secure` и используют префикс `__Secure-`; это следует из режима запуска, а не из написания `NEXTAUTH_URL`. Локальная разработка на `http://localhost` продолжает работать: браузеры считают localhost защищённым контекстом.

## Схема и демо-данные

SQL-файлы находятся в `db/init/`:

- `001_schema.sql` — таблицы `users`, `wishes`, `donations`, `donation_history`, `chat_messages`, перечисления `user_role` и `refund_reason`, внешние ключи и индексы;
- `002_seed.sql` — демонстрационные данные (те же сотрудники, пожелания, суммы и переписка, что и раньше в mock-данных). Все вставки идемпотентны.

При запуске через `docker-compose.yml` каталог `db/init` монтируется в `/docker-entrypoint-initdb.d`, поэтому схема и данные применяются автоматически **только при первом старте на пустом томе**.

> **Ограничение:** изменения в `db/init/*.sql` после создания тома данных автоматически **не применяются**. Чтобы применить изменения схемы, примените их к существующей базе вручную (например, `docker compose exec db psql -U <user> -d <db>`) или удалите том `db_data` (это сбросит демо-данные).

Для Google-входа таблица `users` получила колонку `google_sub` (Google subject id, может быть `NULL`). На **существующем** томе добавьте её вручную:

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS google_sub text UNIQUE;
```

Колонка необязательна, поэтому уже хранящиеся записи остаются читаемыми, а последующие входы продолжают работать. На новом томе колонку создаёт `db/init/001_schema.sql` автоматически.

## Развёртывание: TLS-эндпоинт и стек

Приложение собирается **вне целевого сервера** (сборка Next.js требует больше памяти, чем доступно на хосте на 1 ГБ), а на хост доставляется готовый образ.

### Граница публикации

- На хосте TLS завершает reverse proxy и проксирует запросы на `127.0.0.1:3000`. Публичный адрес — бесплатное динамическое DNS-имя, поэтому сертификат получается без покупки домена, а адрес **не меняется между перезапусками**.
- В `docker-compose.yml` порт приложения привязан к loopback: `127.0.0.1:3000:3000`. Прямой `http://<хост>:3000` снаружи недоступен; приложение доступно **только** через `https://<публичный-хост>`.

### Порядок развёртывания

1. Соберите образ на машине разработки:

   ```bash
   docker build -t corp-gifts-app:latest .
   ```

2. Передайте образ на сервер (например, `docker save` → `docker load`) и скопируйте `docker-compose.yml`, `db/` и `.env`.

3. **Проверка паритета конфигурации.** Сравните файл `.env` на хосте с версией из репозитория, чтобы исключить молчаливый дрейф, который уже приводил к неудачному развёртыванию:

   ```bash
   # список переменных, которые ожидает задеплоенная конфигурация
   diff <(grep -oE '^[A-Z_]+' .env | sort) <(grep -oE '^[A-Z_]+' .env.example | sort)
   ```

   Расхождение должно быть устранено до запуска стека. На Windows используйте `Compare-Object` по списку имён переменных.

4. Запустите стек на сервере:

   ```bash
   docker compose up -d
   ```

   Сервис `app` стартует только после того, как база станет здоровой (`healthcheck` у `db`). Приложение подключается к базе по имени сервиса `db` через `DATABASE_URL`.

5. Настройте консоль провайдера (Google Cloud → OAuth consent screen и OAuth client):
   - **redirect URI**: ровно `https://<публичный-хост>/api/auth/callback/google` (совпадает со значением `NEXTAUTH_URL`);
   - **User type**: `External`. Тип `Internal` допускает только аккаунты одного Workspace и не пустит внешнего проверяющего;
   - **Publishing status**: `In production` (или добавьте проверяющего в `Test users`, пока приложение в статусе `Testing`). Это и есть конфигурация согласия, позволяющая войти человеку, которого **не** регистрировали заранее.

6. Убедитесь, что в `.env` на хосте заданы сильные и различные `NEXTAUTH_SECRET` и `REGISTRATION_TICKET_SECRET`, а сам файл `.env` не отслеживается репозиторием. Запущенное приложение при этом не сообщает об ошибке конфигурации.

Сервисы ограничены по памяти (`mem_limit: 384m` каждый), а PostgreSQL запускается с настройками для малого хоста. Суммарное потребление стека укладывается в бюджет ~700 МБ.

### Автоматическое развёртывание (CI/CD)

Шаги выше описывают развёртывание вручную. Ту же процедуру выполняет workflow `.github/workflows/ci-cd.yml`:

1. **`checks`** — на каждый `push` и `pull_request`: Node 20 с кэшем npm, `npm ci`, затем `npm run lint`, `npm run typecheck` и `npm test`. Красный результат блокирует остальные задачи. Группа `concurrency` отменяет предыдущий запуск на той же ветке.
2. **`build`** — только на `push` в `main`, после успешных `checks`: собирает образ в раннере (на хосте образ не собирается), тегирует его коммитом и `latest`, сохраняет и передаёт артефактом.
3. **`deploy`** — только на `push` в `main`, после `build`: тегирует текущий образ хоста как `corp-gifts-app:previous` (точка возврата), передаёт новый образ по SSH (`docker save | gzip | ssh | docker load`), синхронизирует `docker-compose.yml` и `db/` **без** `.env` и выполняет `docker compose up -d`.

Хост при этом не пересобирает образ и не теряет состояние: `.env` не перезаписывается, том `db_data` не пересоздаётся, миграции не запускаются.

#### Секреты репозитория

Настройте в GitHub → Settings → Secrets and variables → Actions:

| Секрет | Назначение |
| --- | --- |
| `VPS_HOST` | адрес хоста для SSH |
| `VPS_USER` | пользователь SSH для развёртывания |
| `VPS_SSH_KEY` | приватный SSH-ключ пользователя развёртывания (целиком, включая строки `-----BEGIN/END-----`) |
| `VPS_DEPLOY_DIR` | абсолютный путь каталога стека на хосте (там лежат `.env` и `docker-compose.yml`) |

Секреты задаются только в настройках репозитория и никогда не коммитятся.

#### Требования к хосту

- Установлены Docker и плагин `docker compose`.
- Пользователь `VPS_USER` принимает вход по ключу `VPS_SSH_KEY` и имеет право запускать `docker`.
- В каталоге `VPS_DEPLOY_DIR` уже лежит `.env` (значения секретов остаются только на хосте) и совместимый `docker-compose.yml`.

#### Откат

Предыдущий образ остаётся на хосте под тегом `corp-gifts-app:previous`, поэтому откат не требует пересборки:

```bash
cd <VPS_DEPLOY_DIR>
docker tag corp-gifts-app:previous corp-gifts-app:latest
docker compose up -d
```

Либо откатите merge в `main` — следующий успешный запуск развернёт предыдущую версию кода.

## Вход в систему

Вход выполняется через аккаунт Google (OAuth 2.0). **Граница допуска открыта по замыслу**: любой аккаунт Google может попытаться войти и зарегистрироваться, ограничения по домену адреса нет. Это осознанное решение демонстрационного развёртывания, а не защита периметром; для продакшена нужны дополнительные меры (см. «Граница допуска» выше).

- Адрес, подтверждённый Google, — идентификатор пользователя. Если запись с таким адресом есть в справочнике, пользователь входит с ролью из этой записи.
- Идентичность привязана к subject провайдера: если у сохранённой записи уже есть subject и он не совпадает с вошедшим аккаунтом, вход отклоняется; запись без subject привязывает его при первом входе.
- Если адреса в справочнике нет, открывается форма регистрации: полное имя (предзаполнено из профиля Google, можно исправить), дата рождения и отдел. Запись создаётся только после отправки полной формы и всегда с ролью `employee` — зарегистрироваться администратором нельзя.
- Администратор назначается вручную в базе данных:
  `UPDATE users SET role = 'admin' WHERE email = '<адрес>';`
- Сессия хранится в подписанной `HttpOnly`-cookie и не читается клиентским JavaScript; выход очищает её на сервере. **Срок жизни сессии — 12 часов**, после чего она не аутентифицирует пользователя.
- Cookie сессии и ticket регистрации в продакшене помечаются `Secure` и префиксом `__Secure-` независимо от написания `NEXTAUTH_URL`.
- **Демо-вход по тестовым адресам.** При `DEMO_LOGIN=1` на `/login` над кнопкой Google появляется поле тестового адреса и подсказка с двумя адресами: `anna.smirnova@company.com` входит как сотрудник, `alexander.petrov@company.com` — как администратор. Роль берётся из записи в базе, а не из запроса, и создаётся та же подписанная `HttpOnly`-сессия, что и при входе через Google. Принимаются только эти два адреса: любой другой (включая реальный адрес из справочника) отклоняется с сообщением об ошибке и не создаёт сессию. При `DEMO_LOGIN` со значением, отличным от `1` (в том числе не заданном), поле и подсказка не отображаются, а сервер отклоняет демо-вход — остаётся строгий вход только через Google.
- Демо-записи `anna.smirnova@company.com` и `alexander.petrov@company.com` остаются в базе как получатели подарков; в demo-режиме под ними можно войти, но отдельного Google-аккаунта у них нет.

Чтобы настроить вход, создайте OAuth-клиент в Google Cloud, добавьте redirect URI `https://<публичный-хост>/api/auth/callback/google` и заполните `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `NEXTAUTH_SECRET`, `REGISTRATION_TICKET_SECRET`, `NEXTAUTH_URL` и `DEMO_LOGIN` (см. `.env.example` и раздел «Развёртывание»).

## API

Клиент не обращается к базе напрямую — все чтения и изменения идут через серверные Route Handlers:

| Метод и путь | Назначение |
| --- | --- |
| `GET/POST /api/auth/[...nextauth]` | вход через Google, сессия и выход (NextAuth) |
| `POST /api/auth/register` | завершение регистрации нового сотрудника (роль `employee`) |
| `GET /api/users` | справочник сотрудников |
| `GET/POST /api/wishes`, `PATCH /api/wishes/[id]` | пожелания (редактирование — только администратор) |
| `GET/POST /api/donations`, `PATCH /api/donations/[id]`, `PATCH /api/donations/[id]/gift-status` | суммы сборов и журнал (изменения — только администратор) |
| `GET /api/chats`, `POST /api/chats/[userEmail]/messages`, `POST /api/chats/[userEmail]/read` | переписка (сотрудник видит только свою ветку) |
