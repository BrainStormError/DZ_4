# Аутентификация пользователей

Пароля нет. Основной вход — **Google OAuth 2.0** (NextAuth v4, стратегия сессии `jwt`). Идентификатор пользователя — адрес, который подтверждает Google; вручную введённый адрес как доказательство личности не принимается, **кроме** документированных тестовых адресов в demo-режиме (`DEMO_LOGIN=1`), описанном ниже.

## Маршруты аутентификации

| Маршрут | Назначение | Файл |
| --- | --- | --- |
| `GET/POST /api/auth/[...nextauth]` | вход, callback Google, чтение сессии, выход, CSRF | `app/api/auth/[...nextauth]/route.ts` |
| `POST /api/auth/register` | завершение регистрации нового сотрудника | `app/api/auth/register/route.ts` |

Конфигурация провайдера, callbacks и cookie — `lib/auth-options.ts`.

## Решения провайдерского callback

| Ситуация | Результат |
| --- | --- |
| Google не подтвердил адрес (`email_verified !== true`) или адрес отсутствует | вход отклоняется (`signIn` возвращает `false`), сессия не создаётся; браузер возвращается на `/login` с сообщением об ошибке |
| Сохранённая запись несёт subject, отличный от subject вошедшего аккаунта | вход отклоняется (привязка identity к subject провайдера) |
| Подтверждённый адрес найден в справочнике (subject совпадает или отсутствует) | токен получает `userId`, пользователь входит с ролью из записи; ticket регистрации очищается; запись без subject получает его |
| Адрес изменился на стороне Google, но subject совпадает с сохранённой записью | находится та же запись (второй профиль не создаётся) |
| Подтверждённый адрес отсутствует в справочнике | токен помечается как «не зарегистрирован» (`unregistered`), страницы не выдаются; выпускается подписанный короткоживущий ticket регистрации |

Роль и факт существования берутся из записи в БД, а не из токена: `resolveCurrentUser()` загружает строку по `userId` на каждом серверном рендере.

## Демо-вход по тестовым адресам

Управляется переменной `DEMO_LOGIN`: включён только при значении `1` (`lib/config.ts`, `isDemoLoginEnabled()`).

| Ситуация | Результат |
| --- | --- |
| `DEMO_LOGIN=1`, адрес из списка `lib/demo-accounts.ts` (`anna.smirnova@company.com`, `alexander.petrov@company.com`) | вход принимается: `demo` credentials-провайдер (`lib/auth-options.ts`) находит запись по адресу, `jwt`-callback пишет её `userId`, роль берётся из записи |
| `DEMO_LOGIN=1`, любой другой адрес (в том числе реальный из справочника) | вход отклоняется (`CredentialsSignin`), сессия не создаётся, регистрация не запускается |
| `DEMO_LOGIN` не задан или имеет иное значение | сервер отклоняет `demo`-провайдер, поле и подсказка на `/login` не отображаются; Google-вход не затрагивается |

Список показанных и принимаемых адресов — один модуль `lib/demo-accounts.ts`. Демо-вход не создаёт записей и не меняет роли; выпускается та же подписанная `HttpOnly`-сессия, что и при входе через Google.

## Cookie сессии

Cookie выпускает сервер (NextAuth) заголовком `Set-Cookie`; клиентский JavaScript её не читает и не изменяет.

| Атрибут | Значение | Источник |
| --- | --- | --- |
| Имя | `next-auth.session-token`; в продакшене — `__Secure-next-auth.session-token` | `lib/auth-options.ts`, `cookies.sessionToken` |
| Значение | зашифрованный и подписанный JWT (JWE, ключ из `NEXTAUTH_SECRET`) | NextAuth |
| `HttpOnly` | да | `lib/auth-options.ts` |
| `SameSite` | `Lax` | `lib/auth-options.ts` |
| `Secure` | да в продакшене (режим запуска), независимо от написания `NEXTAUTH_URL` | `lib/auth-options.ts` |
| Криптографическая подпись | да (JWE с `NEXTAUTH_SECRET`) | NextAuth |
| Срок жизни | 12 часов (`session.maxAge = 43200` секунд) | `lib/auth-options.ts` |

`NEXTAUTH_SECRET` не задаётся значением по умолчанию: если он отсутствует или оставлен примером из `.env.example`, приложение сообщает об ошибке конфигурации вместо выпуска сессий с известным ключом.

Сервер не хранит таблицу сессий: токен самодостаточен, но роль и существование всё равно сверяются с БД при каждом запросе.

## Cookie ticket регистрации

Выпускается провайдерским callback при неизвестном адресе.

| Атрибут | Значение | Источник |
| --- | --- | --- |
| Имя | `corp-gift-registration`; в продакшене — `__Secure-corp-gift-registration` | `lib/cookies.ts` |
| Значение | HMAC-SHA256 подпись полезной нагрузки (адрес, имя, `sub`, `exp`) | `lib/registration-ticket.ts` |
| Ключ подписи | `REGISTRATION_TICKET_SECRET`, **отдельный** от `NEXTAUTH_SECRET` | `lib/registration-ticket.ts` |
| `HttpOnly` | да | `lib/cookies.ts` |
| `SameSite` | `Lax` | `lib/cookies.ts` |
| `Secure` | да в продакшене | `lib/cookies.ts` |
| `Max-Age` | `600` секунд (10 минут) | `lib/registration-ticket.ts` |

Ticket **подписан отдельным ключом**, **истекает**, **отклоняется при изменении** и принимается только вместе с выпустившей его unregistered-сессией, адрес которой совпадает с адресом ticket (`readRegistrationTicket()` проверяет подпись через `timingSafeEqual` и срок `exp`).

## Разрешение пользователя на сервере

Единая точка — функция `resolveCurrentUser()` в `lib/session.ts`.

| Шаг | Действие |
| --- | --- |
| 1 | `getServerSession(authOptions)` читает и проверяет cookie сессии |
| 2 | Если сессии нет или в ней нет `userId` — вернуть `null` |
| 3 | Загрузить запись `users` по `userId` (`findUserById()`) |
| 4 | Вернуть объект `User` (включая `id` и `role`) либо `null` |

Следствия:

| Ситуация | Результат |
| --- | --- |
| Cookie сессии нет | `null`: API отвечают `401`, страницы уводят на `/login` |
| Сессия есть, но адрес не найден в справочнике (`unregistered`) | `null`: доступ не выдаётся, пользователь направляется на регистрацию |
| Cookie изменена или не подписана | токен не расшифровывается → `null`: запрос неаутентифицирован |
| Старая cookie `corp-gift-auth-email` с «голым» адресом | не читается нигде → запрос неаутентифицирован |
| Запись сотрудника удалена из справочника | `null`: доступ отзывается автоматически без списка сессий |
| Запись есть | валидная сессия с ролью из записи |

## Регистрация нового сотрудника

| Шаг | Действие |
| --- | --- |
| 1 | Callback выпускает ticket `corp-gift-registration` и уводит на `/register` |
| 2 | Форма показывает подтверждённый адрес только для чтения, полное имя (предзаполнено, редактируемо), дату рождения и отдел (обязательны) |
| 3 | `POST /api/auth/register` читает ticket и требует unregistered-сессию с тем же адресом, затем проверяет поля и создаёт запись через `createEmployeeUser()` |
| 4 | Роль всегда `employee`; параметра роли нет — регистрация не может создать администратора |
| 5 | Вставка conflict-safe (`ON CONFLICT DO NOTHING`): повторная или параллельная отправка не создаёт вторую запись и не даёт внутреннюю ошибку; существующий адрес считается уже зарегистрированным |
| 6 | Ticket очищается (расходуется) после успешной регистрации; на следующем запросе `jwt`-callback находит запись и сессия становится полноценной |

Администраторы назначаются вручную в БД, например:

```sql
UPDATE users SET role = 'admin' WHERE email = 'person@example.com';
```

## Выход из системы

| Действие | Источник |
| --- | --- |
| `POST /api/auth/signout` (NextAuth) очищает cookie сессии | `lib/auth-context.tsx` (`signOut`) |
| Сброс состояния `user` в React | `lib/auth-context.tsx` |

Старый механизм выхода через `document.cookie` удалён; после выхода защищённые страницы больше не выдаются.
